# 历史定位与版本合并

需要确定比较基准、连续补充同版本或将预览变化合并为正式版时读取。

## 确定历史边界

先确认仓库、remote、当前分支和工作区；Bugaoshan 的 `origin` 可能是个人 fork，不能默认它就是组织上游。使用明确的 revision 分析，远端需要更新时再 fetch，避免为了读历史 checkout、pull 或 rebase 当前工作区。

基准应同时满足代码与发布语义：

- **单个预览版**：用户指定比较范围时用该范围；否则核对上一实际发布的同周期预览及其 tag。失败构建可能已经创建 tag，不能把“有 tag”当成“用户已拿到该版本”。
- **首次预览或完整发布周期**：通常以上一个已发布正式版为基准；检查该 tag 是否位于目标代码的历史上，不仅按版本大小取全仓库最高 tag。
- **正式版**：以上一个正式版为用户基准，覆盖整个本次发布周期，包括其中已经对预览用户发布的变化。
- **同目标版本增量**：找到前一轮说明实际覆盖到的 SHA，再分析该 SHA 到本轮终点的差异。只追加变化，不重新推翻已确认文案和收录边界。

用户只说“补充后续提交”却找不到旧覆盖点时，可结合 changelog 修改历史、用户给出的范围和既有条目核对；不能简单把“写 changelog 的 commit”当作所有代码的覆盖终点。仍有歧义时报告假设并补问，不编造无遗漏保证。

示例命令中的 `BASE`、`TARGET`、`COMMIT` 替换为已核实的 revision：

```powershell
git status --short
git remote -v
git tag --list --sort=-version:refname
git merge-base --is-ancestor BASE TARGET
git -c core.quotepath=false log --encoding=UTF-8 --format="%H%x09%an%x09%s" BASE..TARGET
git diff --stat BASE TARGET
git show --format=fuller --no-ext-diff COMMIT
git show -s --format=%B COMMIT
```

标题不清楚时读具体 diff。merge、squash、跨分支合并和 revert 会影响条目归属，不能只扫描标题或把 merge 消息再算一条。需要作者归属时，正文 trailer 和 PR 记录可补充 squash 后的协作者。

Windows 输出乱码时先确保读取工具与 `git log --encoding=UTF-8` 使用一致编码，必要时以 UTF-8 写临时文件再读取；不要对已经正确的 UTF-8 文本再次猜测转码。

## 预览版晋升正式版

1. 确认目标正式版本、上一正式版、同周期实际发布的预览/RC、最终代码 revision。
2. 收集已确认的预览说明，按功能而非按预览版本顺序分组，合并重复描述；已被后续修正的内容以最终状态为准。
3. 核对最后一个已覆盖预览到正式版终点的新增提交，仅对增量补做详细分析；已有条目有矛盾、遗漏或证据不足时针对性回查，不默认全部正确，也不无故重做全周期分析。
4. 新功能在本周期内经历的内部修复并入功能本体；上一正式版已经存在的功能修复仍保留为修复项。已发布预览回归可在对应预览说明中体现，正式版条目则以正式用户的基准整理。
5. 补充最后生效的平台、系统和功能入口限制，形成一个目标正式版章节。其他历史版本保持原状，除非用户要求归并历史预览章节。
6. 用户要求 Highlights 时沿用此前精选，结合增量重新权衡，不因正式版发布而自动重写没有变化的亮点。

没有足够的预览说明时直接分析明确的正式版范围；来源缺失要如实说明，不能假定每个预览都已有完整文案。

## 发布内容边界

版本推导和构建由现有脚本管理：预览版本与包体版本可能不同，`pubspec.yaml` 也可能仍为上一正式版。本 skill 不复制版本推导算法，不从表面版本号猜测目标范围，也不因整理文案而打 tag、推送分支或触发发布。

网站版本页由独立文档仓库的发布同步生成；文案修正应在其源头处理，不能仅手改自动生成页面后声称发布说明已更新。
