# Bugaoshan Changelog

以目标版本和明确的提交范围集中整理更新说明，描述最终生效的变化。日常提交是取证材料，不能直接逐条转抄为发布说明。

## 输入与范围

- 必要输入是目标版本、目标代码 revision、比较基准和现有 `CHANGELOG.md`。目标可为正式版或带后缀的预览版。
- 版本来自用户明确指定、目标 Release PR 或可信的发布上下文。tag 用于确定历史边界，不据此猜测下一个版本；`pubspec.yaml` 可能仍是上一正式版，也不能自动当成目标版本。
- 缺少目标版本时，先梳理可确定的提交与变更，向用户补问版本；不把猜测的版本号写入文件。日期以用户指定的发布时间为准，未确定时先省略日期，不把生成当天自动当成发布日期。
- 用户只要文案时输出最终 Markdown；要求更新文件时定点修改对应版本。整理 changelog 不自动包含修改版本号、生成商店元数据、提交、推送或发布。
- 内容规范见根 `AGENTS.md` 和 `CHANGELOG.md`；本 skill 采用按目标版本集中整理的流程。确定历史范围或合并预览版说明时读取 [历史定位与版本合并](references/history-and-release.md)。

## 工作流程

### 1. 确定覆盖范围

记录本次基准与终点 SHA，确认需要整理的是完整版本、同版本增量，还是预览版晋升正式版。

- 用户明确给出 tag、PR 或提交范围时优先采用，并确认它与目标版本对应。
- 自行寻找基准时，核对 tag 指向、可达性与发布状态；最新的 tag、最高版本号及最近创建的 Release 不一定是本次正确基准。
- 增量补充以已有文案实际覆盖到的提交为界；已有 changelog 的最后一次修改提交未必就是其覆盖终点。
- 基准不明确时，先核对现有条目和相关提交，再缩小差异范围。无法确认的部分标为待核对，不能声称已经完整覆盖。

### 2. 核对最终效果

先用提交标题定位，再读相关 diff、调用点、测试和作者说明。提交类型、PR 标题及机器人/AI 摘要只能提供线索，不能代替实际行为。

重点确认功能是否已有可用入口、适用平台/系统/学生类型、认证与网络前置条件、用户是否真的能使用。查 `lib/l10n/app_zh.arb` 使用界面正式名称，必要时对照 `app_en.arb`；不将内部类名、Provider 名或开发者别称当成产品名称。

代码支持某个平台不等于该平台已发布可下载制品。下载渠道、商店状态、签名和分发范围分别核实，不把验证包写成正式安装包。

### 3. 合并净变更

- 同一功能的新增、后续修复、调整和回归处理合并成最终有效的变化；同一 PR 含多个独立功能则拆开。
- 首次出现在本发布周期的新功能，以完整功能为主条目，开发期间的内部修补并入其中。若回归影响了已经发布的预览版用户，可在后续预览版说明中保留修复；晋升正式版时再按正式用户的基准合并。
- 完整撤销的变更不收录；部分撤销只描述最终保留部分。无法仅凭标题判断时检查 diff 和撤销后的实现。
- 多平台表现相同时合并描述；生效条件或效果不同则分别说明。不能把只在 iOS、Android 特定系统或研究生场景生效的变化写成全平台通用。
- 既有条目与新增提交描述同一件事时更新原条目，不重复追加。保留用户已经确认的收录、暂缓和定性，只有新证据改变状态时再调整并说明。

### 4. 筛选与分类

面向 App 用户保留显著功能、可感知的体验变化和缺陷修复。内部重构、测试、格式、工具链、开发规范、无产品效果的 CI/文档改动通常不收录；任何提交前缀都不能替代对实际效果的判断。维护提交若修复了安装、更新或运行问题，应写出该用户效果。

自动版本号/tag 提交、重复生成的 changelog/元数据、合并记录和已完全撤销的变化不作为独立条目。`[skip changelog]` 标记表示排除该提交，但不应连带丢弃同一功能链中其他提交的有效变化。

| 分类 | 内容 |
| --- | --- |
| `Added` | 新功能、新入口、新的平台或服务支持 |
| `Changed` | 用户可感知的行为、外观、性能或兼容性改进 |
| `Fixed` | 已有行为的缺陷、异常、回归或兼容性修复 |
| `Removed` | 用户可见功能或支持范围的移除 |

只保留有条目的分类，顺序沿用上表，不为内部维护额外添加分类。

### 5. 文案、引用与排序

- 中文为主，列表用 `-`，按用户影响和重要性排序。每条写清“哪里发生了什么变化”，必要时补充触发条件与限制。
- 优先写结果和可理解的功能名；技术机制只在解释使用条件、数据影响或临时限制时出现。实际可感知的优化才写，不把所有重构概括成性能提升。
- 已确认的 issue/PR 引用随合并保留，使用现有 `(#编号)` 风格；仓库不明确时用完整链接。不要将多个提交的引用误认为多个不同问题。
- 作者署名按用户要求和现有风格处理。需要署名时查 author 与 `Co-authored-by`，必要时核对 PR；committer 不等于贡献者，显示名不等于 GitHub login。
- 用户要求 Highlights 时，从本次发布周期的有效变化中精选少量亮点；后续增量在已有亮点上补充、合并或替换，避免只写最新提交。通常无需重复整份双语说明或为每个历史版本添加折叠结构。

## 版本章节与交付

沿用本仓库可解析的方括号版本标题，例如：

```markdown
## [X.Y.Z] - YYYY-MM-DD

### Added
- 新增功能及其使用条件。

### Changed
- 调整后的用户可见行为。

### Fixed
- 修复触发条件下的具体问题（#123）。
```

预览版标题使用完整目标版本，如 `[X.Y.Z-preview.2]` 或 `[X.Y.Z-rc1]`；日期未定时使用 `## [目标版本]`。示例中的空分类和占位文本应在实际输出中省略或替换。

写入前检查同名章节；已有章节应合并更新，重复执行不能产生第二份同版本内容。保留其他历史版本，除非用户明确要求合并或修正它们。新版本放在版本历史顶部，不顺带全量重排旧文案。

预览版晋升正式版时，优先合并已确认的同周期预览说明，核对正式版基准和最后一个预览之后的增量，不机械拼接整个 git log。详细流程见 [历史定位与版本合并](references/history-and-release.md)。

交付前确认：

- 基准、终点和目标版本对应；没有把已发布的旧变化重新当成本次新增。
- 同功能已合并、撤销已处理、重复项已去除，所有保留条目都有事实依据。
- 平台、版本、学生类型、网络和分发限制准确；未公开的入口没有写成已开放。
- 版本标题、分类、日期和引用符合当前输出约定。
- 写文件时只修改授权范围，并检查 `git diff --check`。文件不在 Git 跟踪范围时另查空白与编码。

纯文案请求仅输出所需的最终 Markdown。文件编辑完成后简短报告修改位置、实际覆盖范围和仍有疑问的条目；不要把分析备注写进对外 changelog 正文。
