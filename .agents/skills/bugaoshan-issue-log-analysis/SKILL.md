# Bugaoshan Issue 与运行日志分析

将用户现象、实际运行版本、日志时间线和代码连成可核对的证据链。日志结构和业务判断以 Bugaoshan 的实现为准。

## 范围与入口

- `#123` 默认指 `The-Brotherhood-of-SCU/Bugaoshan` 的 issue；完整 URL 按实际仓库读取，先确认是否为 Bugaoshan 或其 fork。
- 也接受用户直接提供的 `.log`、粘贴文本、截图、录屏和环境信息，不要求 GitHub issue 或固定命名的压缩包。
- 分析默认产出结论和建议。修代码、提交、评论、关闭 issue 等操作按用户实际授权执行；分析附件不等于授权操作学校服务。
- 先读仓库根 `AGENTS.md` 和 [运行日志架构](../../../docs/architecture/logging.md)。分析日志时读 [日志证据说明](references/log-evidence.md)；定位到具体业务或需要修复建议时再读 [诊断与代码定位](references/diagnosis.md) 的相关部分。

## 分析流程

### 1. 确认现象、版本与证据范围

读取 issue 正文、相关评论和可访问附件；已有评论、机器人判断和 AI 摘要只作线索。记录：

- 用户想完成的操作、实际结果、复现步骤与大致发生时间。
- 平台和系统、应用版本、构建号、正式/预览/自编译渠道，以及环境信息中的 Tag / Commit；诊断需要时补充设备型号、学生类型、校园网或 VPN 状态。
- 附件来自“复制全部”“保存并分享”、原始轮转文件还是筛选后的截图；是否发生过重启、清空、关闭落盘或清理缓存。

导出头的 `exported` 是导出时间，`entries` 是当前内存条数，都不是故障发生时间或完整历史条数；头部没有应用版本，不能据此推断版本。

没有日志也可利用清晰的错误文本、截图或复现步骤做初步定位。只有模糊现象时，简短说明尚不能确定原因，并指出最有用的缺失材料及获取方式；不编造根因、不套完整报告模板。

### 2. 建立时间线

按 [日志证据说明](references/log-evidence.md) 识别历史与内存分段、记录边界、轮转顺序和证据缺口，再围绕复现时间读取上下文。

先找用户所见错误、相关 tag 和首个异常，保留其后续的认证恢复、重试结果、Provider 状态及界面变化。不要停在第一条 `WARN`；也不要只凭最后一个全局异常标签认定责任模块。

导出中的日期时间未带时区，必要时与用户设备时间核对。历史文件可能跨启动，旧日志里出现的问题不自动等于当前复现；没有进程标记时应说明边界不确定。

### 3. 对照用户版本与当前实现

- 先按 tag 搜索记录调用点，再沿页面/Provider、API、子系统认证和统一认证追踪实际调用关系；堆栈与状态变化应相互支持。
- 用户版本优先使用环境信息中的 Commit，其次是可确认的 tag。用 `git show REV:path`、`git log`、`git blame` 复核旧实现，避免为读旧代码切换或改动用户工作区。
- 缺少可解析的版本时，把当前代码作为假设并注明；不能用当前实现否定旧版本日志。
- 声称“已经修复”前核对修复提交，并区分它是否已进入用户可获取的对应平台、渠道版本。分支合入或存在测试不等于已经发布。
- 输出按钮、设置和入口名时查 `lib/l10n/app_zh.arb`；英文回复查 `app_en.arb`。内部 tag 可括注保留，不能把它当成用户界面名称。

### 4. 形成可执行判断

分清已证实的直接失败、可能的上游原因和尚缺的证据。日志未覆盖对应故障时写明“本次材料未覆盖/未复现该现象”，不能据此断言没有问题。

修复建议应沿用已有的认证恢复、状态管理和日志机制。若当前日志不足，指出需要在何处补操作说明、异常或状态变化；不要用无限重试、吞异常或扩大日志数据采集代替根因分析。

用户同时提出产品诉求时，再区分其根本需求与指定方案，结合设计约束、现有替代路径、影响面和维护成本评估合理性、必要性和优先级。相关实现、历史提交和同类 issue 是判断依据，不能仅凭维护者旧评论或“功能较新”降低真实缺陷的优先级。

## 输出

默认使用中文，先给结论与置信度，再按问题复杂度保留以下内容，省略没有信息的部分：

- **现象与环境**：版本、平台、操作和故障时间；注明实际查阅的代码 revision。
- **关键证据**：少量原始日志及附件文件名/行号、必要的截图和代码依据；保留异常的 `error:` 与相关堆栈，不倾倒整份日志。
- **原因与不确定性**：证据链、恢复结果、候选原因及尚缺材料；区分学校服务/网络、认证、业务数据、界面、平台和日志系统自身的问题。
- **用户可做的事**：有依据的重试、升级或临时绕过方法；需要补材料时给准确导出步骤。优先留存现场再建议重置、清理或重新安装，并说明会影响的数据。
- **开发者后续**：有证据支持的修复位置和最小验证方式；交接给修复者时附现象、脱敏原文、实际版本和待验证假设。
- **诉求评估**：仅当报告包含功能或设计请求时展开。

为外部 issue 准备回复时，代码依据用实际分析 revision 的 GitHub `blob` 永久链接，并确认行号；仅存在本地的实现应明确标注。英文 issue 或用户要求时提供英文，不固定重复整份双语报告。
