# ADR-0011：课表日期为数字格式，顺序与分隔符跟随系统语言

- 状态：已接受并实施
- 决策日期：2026-10-26（2026-10-31 按评审意见收敛为跟随 CLDR）

## 背景

课表顶栏与网格表头的日期此前走两条互不相干的路径：顶栏按语言拼出
`2026/10/18`（窄屏省年份，仅英文资源里带 `MM/DD` 文案），表头则用
`dateMonthDayCompact` 输出 `10/19`，而中文的 `dateMonthDay` 仍是「10月19日」。
结果是同一屏里出现两种顺序、两种分隔符，且中文长日期在窄列里被
`FittedBox` 压缩到难以辨认——低分辨率屏上 5~7 列平摊后每列只有 60px 上下。

初版曾提供九种完整日期写法（顺序 × 分隔符 × 年份位数）。评审指出两点：
选项太多，且「日月反转」的写法在没有年份锚点时容易误读。于是先收敛为
「顺序跟语言、分隔符二选一」，进一步实测发现 CLDR 连分隔符也一并给出，
最终收敛为零设置项。

## 决策

日期格式的**顺序与分隔符都取自当前语言环境的 CLDR 数据**，不写死在 ARB，
也不做成用户设置。`DateDisplayFormat.of(locale)` 读取 `intl` 的
`DateFormat.Md(locale).pattern`：

| locale | CLDR 模式 | 表头 | 顶栏 |
|---|---|---|---|
| zh_CN | `M/d` | 08/19 | 08/19/2026 |
| en_US | `M/d` | 08/19 | 08/19/2026 |
| en_GB | `dd/MM` | 19/08 | 19/08/2026 |
| de_DE | `d.M.` | 19.08 | 19.08.2026 |

从模式里取两件事：`M` 与 `d` 的先后决定顺序，第一个 `/`、`.`、`-` 决定分隔符。
月与日补零到两位、年份恒为四位，保证窄列宽度与语言无关。CLDR 数据缺失时回落
`M/d`。

两种消费方式：

1. `formatFull`：课表左上角顶栏，带年份。
2. `formatMonthDay`：网格表头每一列，只留月与日。

日期与节假日弹窗（`special_day_sheet`）与课表导出图片同样使用
`formatMonthDay`，与点开的表头列保持一致。

**没有设置项**。初版曾提供九种完整日期写法，评审后收敛为「顺序跟随语言 +
用户选分隔符」两个维度；进一步实测发现 CLDR 连分隔符也一并给出，于是连
分隔符选择也去掉：用户要改格式，改界面语言即可。

落地范围限定在课表域：顶栏、表头、特殊日弹窗、课表导出图片。其余页面
（考试安排、提醒设置、校历等）的日期文案不在本次范围内，仍按各自现状输出。

历法语义不变：日期仍由 `ScheduleConfig.dateForCourseDay` 计算，本格式只决定
渲染文本，不参与任何周次或日期计算。

## 后果

正面影响：

- 同一屏内顺序、分隔符统一，且不再随界面语言的文案长度变化。
- 表头宽度恒定，低分辨率屏与中文界面不再被长日期挤压。
- 零设置项、零格式术语，用户不需要理解「年份位数」「分隔符」。
- 新增语言无需改代码，CLDR 有数据即自动正确。

代价与约束：

- 用户无法单独覆盖格式；想换顺序或分隔符只能切换界面语言。这是刻意取舍：
  顺序误读的代价高于少一个选项。
- 依赖 `intl` 的 locale 数据已在 app 内初始化（由 `flutter_localizations`
  提供）；纯 Dart 单测里需先 pump 带 delegate 的 MaterialApp。
- 中文用户不再看到「10月19日」这类母语写法，为窄列可读性做的取舍。
- 该偏好只覆盖课表；若后续要求全 App 统一，需要逐个替换写死 `yyyy-MM-dd`
  的页面，并重新评估哪些页面属于「窄空间」。
- 自定义格式（任意排列组合）不开放，避免无法穷举的下拉项与溢出回归面。
